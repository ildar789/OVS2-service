# Lab3 Demo App

Демонстрационное веб-приложение (Node.js/Express) для лабораторной работы
по реверс-прокси Apache/Nginx с балансировкой нагрузки, DNS-балансировкой,
TLS-терминацией и обработкой асинхронных запросов.

## Как реализованы требования задания

1. **Идентификация backend-узла.**
   - Страница `/` показывает блок «Узел, обработавший этот запрос»
     (instance_id, hostname, pid, порт, время).
   - JSON-эндпоинт `GET /api/info` отдаёт те же сведения в машиночитаемом виде.
   - Каждая заметка в общей таблице `notes` хранит `created_by_node` —
     видно, какой узел её создал.

2. **Хранилище данных, устойчивое к падению узла.**
   - Данные (`notes`) хранятся в **внешнем PostgreSQL**, общем для всех
     backend-узлов, а не локально на каждом узле.
   - Пользовательские сессии хранятся в **внешнем Redis** через
     `connect-redis`, а не в памяти процесса (`MemoryStore` не используется)
     и не в локальных файлах.
   - При недоступности БД/Redis приложение не падает, а отвечает кодом
     `503` и пытается восстановить соединение на следующих запросах —
     это позволяет балансировщику направить трафик на другой узел
     и/или на другой инстанс хранилища без потери работоспособности
     кластера в целом.
   - `GET /api/health` — health-check эндпоинт для Nginx/Apache,
     проверяющий доступность обоих внешних хранилищ.

3. **Приложение не занимается TLS/SSL.**
   - Сервер слушает только обычный HTTP (`app.listen(PORT)`), сертификаты
     нигде не подключаются. `app.set('trust proxy', 1)` включён, чтобы
     корректно читать `X-Forwarded-For`/`X-Forwarded-Proto` от прокси.
   - Cookie сессии не помечена `secure`, так как TLS видит только прокси —
     это сознательное решение, соответствующее ограничению №3.
   - Примеры конфигураций для терминации TLS на Nginx/Apache — в папках
     `nginx/` и `apache/` (используются в следующей лабораторной работе).

4. **Сессии — не в памяти и не в локальных файлах.**
   - `express-session` + `connect-redis`, хранилище — внешний Redis.
     При падении одного backend-узла сессия остаётся доступной для
     остальных узлов, так как её состояние не привязано к процессу.

5. **Асинхронная обработка запросов.**
   - Все обращения к БД/Redis выполняются через `async/await`.
   - `GET /api/async-task` — демонстрационный эндпоинт, имитирующий
     обращение к внешнему сервису со случайной задержкой, показывает
     неблокирующую обработку в Node.js event loop.

## Запуск (2+ идентичных узла локально)

```bash
docker compose up --build
```

После запуска будут доступны:
- узел 1: http://localhost:3001
- узел 2: http://localhost:3002

Оба используют один и тот же образ (`./app`), отличаются только
переменной окружения `INSTANCE_ID` и внешним портом — это и есть
«два и более идентичных экземпляра».

Чтобы добавить третий узел — скопируйте блок `app2` в
`docker-compose.yml`, задайте `INSTANCE_ID: node-3` и свободный внешний порт.

## Проверка балансировки вручную (без прокси)

```bash
curl http://localhost:3001/api/info
curl http://localhost:3002/api/info
```

Значения `instance_id`/`pid` будут различаться — это подтверждает,
что перед вами два независимых процесса.

## Проверка устойчивости хранилищ

```bash
docker compose stop app1
curl -s -c cookies.txt http://localhost:3002/         # сессия и заметки доступны
docker compose start app1
```

Отключение одного backend-узла не приводит к потере данных или сессий,
так как оба узла обращаются к одним и тем же `postgres`/`redis`.

## Подключение реверс-прокси (лаб. работа №3)

1. Поднимите Nginx или Apache перед `app1`/`app2` (см. примеры конфигов
   в `nginx/` и `apache/`).
2. Настройте TLS-сертификаты на прокси (самоподписанные или Let's
   Encrypt) — приложение об этом ничего не знает.
3. Для DNS-балансировки создайте несколько A/AAAA-записей, указывающих
   на IP прокси-узла(ов) (round-robin DNS), либо настройте
   балансировку на уровне DNS-провайдера/GSLB — это выполняется вне
   приложения и вне Nginx/Apache конфигурации.
4. Для L4-балансировки перед Nginx/Apache можно использовать, например,
   `HAProxy` в режиме `tcp` или `keepalived` + `IPVS` — приложение не
   требует изменений, так как ничего не знает о деталях транспортного
   уровня.

## Переменные окружения

| Переменная       | Назначение                                   | По умолчанию                                      |
|-------------------|-----------------------------------------------|----------------------------------------------------|
| `PORT`            | порт HTTP-сервера                             | `3000`                                              |
| `INSTANCE_ID`     | идентификатор узла (для отображения)          | hostname контейнера                                 |
| `DATABASE_URL`    | строка подключения к PostgreSQL               | `postgresql://lab3:lab3pass@postgres:5432/lab3db`  |
| `REDIS_URL`       | строка подключения к Redis                    | `redis://redis:6379`                               |
| `SESSION_SECRET`  | секрет для подписи cookie сессии              | `change-me-in-production`                          |
